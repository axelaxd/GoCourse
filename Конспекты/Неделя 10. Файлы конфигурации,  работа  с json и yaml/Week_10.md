# Файлы конфигурации

### Работа с json и yaml

**Сериализация** - процесс преобразования в формат (struct -> JSON/YAML, `json.Marshal`)

**Десериализация** - обратный процесс, когда из строки или файла снова создаётся объект (JSON/YAML -> struct, `json.Unmarshal`)

1. **Главная библиотека** - `encoding/json`
#### YAML
Более дружественный человеку текстовый формат сериализации данных. Подходит для удобного хранения конфигурации больше, чем `JSON`

```
server:
    port: 8080
    host: localhost
app:
    log_level: 2
    enabled_test: true
    
test: null
dev: ["local", "stage", "prod"]
```

В отличие от `JSON` формат `YAML` поддерживает комментарии, что также упрощает работу с ним.

```
this_is_string: !!str 67.43
```

Объявляя тип `!![тип]`, мы даем понять, что именно ожидаем при парсинге файла

Также `YAML` имеют возможность создавать внутри себя якоря/алиасы, тем самым позволяя переиспользовать значения

Якоря начинаются с `&` перед неймингом:

```
default: &default_settings
	port: 8080
	
local:
	<<: *default_settings
	host: localhost
```

В целом формат позволяет работать с данными намного глубже и вариативнее, чем это позволяет делать `JSON`. Именно поэтому он и используется для конфигурационных файлов больше.

Фан-факт: ты можешь встретить файлы с двумя различными форматами — `.yml` и `.yaml`. Оба правильные, но предпочтительнее использовать второй вариант

#### Теги структур
Структуры - самый качественный способ организации данных. Их поля должны содержать определённые теги, по которым рантайм поймёт, как и куда складывать данные из файлов.

Например:
```
type Config struct {
	Port int
	Host string
}
```

Эта структура вряд ли чем-то поможет. Делаем небольшое движение рукой и получаем:

```
type Config struct {
	Port int      `json:"port" yaml: "port"`
	Host string   `json:"host" yaml: "host"`
}
```

Теги - это метаданные полей. 

Если говорить про `JSON`, то пакет `encoding/json` по умолчанию сериализует только **экспортируемые** поля структуры, используя имена полей, как имя json-ключа, если тег этому полю не задан. Если поле в структуре не экспортируемое, то и json-пакет с ним работать **не будет**.

```
type Config struct {
	Port int    `json:"port" yaml:"port"`
	host string `json:"host" yaml:"host"` // не сериализуется
}
```

Но json-теги могут быть не просто именем ключа/поля. Можно управлять сериализацией более гибко:

```
type User struct {
    Name     string `json:"name"`             // Обычный кейс
    
    Surname  string `json:"last_name"`	      // Разные имена
    
    Age      int    `json:"age,omitempty"`    // Дефолт имя
    
    Password string `json:"-"`                // Исключается
    
    Address  string `json:",omitempty"`       // Дефолт - пустая
    
    Phone    string `json:",string"`          // В json-строку
    
    HasJob   bool   `json:"has_job,omitzero"` //
    
    Foo      *int   `json:"foo"`              //
}


func main() {
	// Создаем экземпляр User
    user := User{
        Name:    "John",
        Surname: "Doe",
        Age:     30,
        Phone:   "123456",
        HasJob:  true,
        // Password не задана — она будет проигнорирована при JSON
        // Foo — nil указатель
    }
    
    // Сериализуем в JSON
    jsonData, _ := json.Marshal(user)
    fmt.Println(string(jsonData))
}
```


`omitempty` - пропускает значения при создании json-объектов, если они дефолтные для типа - `zero values`

`omitzero` - позволяет убирать именно нулевые значения для всех типов, с которыми не мог работать `omitempty`

```
response := answer{Key: "value"}

b, err := json.Marshal(response) // Преобразуем go-объект в json-строку (байты)
if err != nil {
	panic(err)
}

fmt.Println(string(b)) // {"key":"value"}
k := answer{}

err = json.Unmarshal(b, &k) // Обратное действие: превращение json-строки в структуру

if err != nil {
	panic(err)
}
```

#### JSON VS YAML

- `JSON` стоит выбрать, когда нужен строгий, простой, машинный формат;
- `YAML` требуется при наличии большого конфига и частой редактуры человеком.

#### Переменные окружения

Ещё одним источником конфигурации для приложений могут служить переменные окружения. Это набор строковых пар `key=value`, хранящихся в операционной системе вне кода программ, то есть обеспечивающих универсальность параметров в различных средах для набора программ, запускаемых в них.


У переменных окружения есть три сильные стороны:

- Они легко меняются без пересборки самой программы.
- Они не привязаны к языку или платформе.
- Их удобно подставлять при запуске, не храня секретные данные в исходном коде.

2. **Раскрыть значения переменных окружения** - `go env`

Переменные окружение можно считывать прямо из кода Go. Например, в MacOS можно добавить свою переменную в `~/.zshrc`, записав в конец:
```
export APP_PORT=":8080"
```

После сохранения используем команду:

```
source ~/.zshrc
```

В мини-программе на Go можно обнаружить значение этой переменной:
```
func main() {
	fmt.Println(os.Getenv("APP_PORT"))
}
```

**Важно** ещё и то, что переменные окружения — это строки. А значит, после получения значения переменной, его стоит провалидировать и преобразовать в нужный тип.

3. **Про файл окружения** - `env`
	Существует полезная для работы библиотека `joho/godotenv`, которая через функцию `godotenv.Load()` загружает переменные из файла `.env` в саму систему, а мы через `os.Getenv` можем загрузить конфигурации в код

```
import "github.com/joho/godotenv"

func main() {
    godotenv.Load() // Загружает переменные из .env в систему
    val := os.Getenv("MY_VAR")
}
```

Но мы часто встречаемся с ситуацией, когда для одного сервиса может существовать один-другой десяток переменных. Что делать с этим? Вызывать на каждый чих `os.Getenv` как-то грустно.

На встречу приходит ещё одно решение в виде библиотеки `caarlos0/env` и тегов полей структуры:

```
package main

import (
    "fmt"
    "log"
    "github.com/caarlos0/env"
    "github.com/joho/godotenv"
)

// Определение структуры с тегами `env`
type Config struct {
    DBHost  string `env:"DB_HOST"`
    DBPort  int    `env:"DB_PORT"`
    APIKey  string `env:"API_KEY" envDefault:"12345678"` // умолч.
    Debug   bool   `env:"DEBUG"`
}

func main() {
    // Загружаем .env-файл (если он есть)
    if err := godotenv.Load(); err != nil {
        log.Println("No .env file found, relying on environment variables")
    }
    
    // Создаём экземпляр структуры
    cfg := Config{}
    
    // Парсим переменные окружения в структуру
    if err := env.Parse(&cfg); err != nil {
        log.Fatalf("Error parsing env: %v", err)
    }
    
    // Теперь переменные в структуре
    fmt.Printf("Config: %+v\n", cfg)
    fmt.Println("Database Host:", cfg.DBHost)
}
```

**Заметь**, что используется специальный тег `envDefault`, который говорит о том, что если такой переменной нет, то библиотека будет взаимодействовать с кодом и подставлять указанное значение

Когда стоит использовать `.env`? В случае локальной разработки или в CI

#### Дефолтные значения

**Всегда** стоит предусмотреть для критичных параметров конфигурации дефолтные значения.

В случае с `.env`, это специальный тег. При работе с флагами мы тоже можем устанавливать значение по умолчанию:
```
// Имя, дефолт значение, описание
port := flag.Int("port", 8080, "Порт сервера")
```
