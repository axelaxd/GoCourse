# Тулинг в Golang

Код должен быть удобен для чтения. Но и не только для тебя но и для твоих коллег

#### Зачем нужен тулинг

- Для того чтобы выдерживать единое оформление кода в разных файлах в условиях одновременной разработки сервиса несколькими разработчиками.
- Это также возможность избегать странных конструкций, которые сам компилятор пропускает (например, функцию с множеством циклов, которые повышают когнитивную нагрузку на разработчика при чтении кода).
- Ещё тулинг помогает чистить импорты, дублирование кода.
- Определяется проблема с конкурентностью и зависимостями.

**Идея проста:**
Пишем код => форматируем его => проходим статические проверки => проходим тесты => коммитим код в ревью

В Golang имеется два типа инструментов, которые можно использовать:

1. Встроенные в экосистему:
- `gofmt`;
- `go test`;
- `go vet`;
- `go doc`.

1. Внешние инструменты:
- `gopls`;
- `goimports`;
- `golangci-lint;`
- `govulncheck`.

Здесь важно понять, что это те самые инструменты, с которыми разработчики вплотную работают повседневно.

Нам необходимо установить три инструмента, пропишем команды:

```
go install golang.org/x/tools/gopls@latest
go install golang.org/x/tools/cmd/goimports@latest
go install golang.org/x/vuln/cmd/govulncheck@latest
```

#### Встроенный тулинг Golang
**Форматирование кода**

В Go о форматировании не спорят. Требуется всего-навсего использовать стандартный форматер `gofmt`

Можно отформатировать все файлы текущей директории и все её поддиректории:
```
go fmt ./...
```

Но также можно отформатировать конкретный файл:
```
gofmt -w file.go
```

Весь проект можно отформатировать командой:
```
gofmt -w .
```

#### Более умное форматирование
`goimports`  - мало того, что автоматически обновляет строки импорта, удаляя и добавляя недостающие зависимости, она еще и форматирует код ровно так же, как и `gofmt`!

Запускается:
```
goimports -w main.go # Форматирование конкретного файла

goimports -w . # Форматирование всего проекта
```

#### Как организована помощь в редакторе
Форматеры помогают после написания кода привести его в порядок. Но утилита `gopls` делает иное: она помогает непосредственно во время работает.

Подобный сервер позволяет интегрировать в IDE определённые возможности для работы с конкретным языком:

- `подсветку ошибок в редакторе;
- `переходы к определению функции/переменной;`
- `поиск использования функций/переменных;`
- `автодополнение;`
- `встроенные подсказки.`

Если честно говорить, то редактор без `gopls` - это не самый лучший редактор для Go. Утилита позволяет увидеть множество проблем в коде ещё до запуска тестов и линтеров.

1. **Очищение кода от подозрительных вещей** - `go vet`
	Позволяет очищать странный и неидиоматичный код

- проверка бесполезных объявлений переменных;
- проверка типичных ошибок при работе с пакетом `sync/atomic`;
- проверка неиспользуемого кода и многое другое.

Важно, что `go vet` не гарантирует, что в коде не останется проблем. Он только ищет странные вещи

```
go vet ./...
```

2. **Линтеры** - `golangci`
	Класс инструментов, которые автоматически проверяют исходный код на наличие ошибок и стилевых нарушений

- проверка на ограничение длины строки;
- проверка на цикломатическую сложность;
- проверка на длину функции и так далее.

Это очень удобный и гибкий инструмент, который не только запускает несколько линтеров, но и быстро работает, выводит всю информацию после аналитики со ссылками на строки

Примером настройки `golangci` через yaml может служить файл:

```
run:
  timeout: 5m
  modules-download-mode: readonly
  
linters:
  disable-all: true # Отключить всё по умолчанию
  enable:          # Что включено принудительно
    - errcheck     # Проверка необработанных ошибок
    - goimports    # Проверка импортов
    - golint       # Рекомендации по стилю (устаревает, но полезен)
    - govet        # Тот самый go vet!
    - staticcheck  # Статический анализ
    - unused       # Неиспользуемый код
    - gosimple     # Упрощение кода
    - bodyclose    # Закрытие http тел
    - dupl         # Поиск дублирования кода
    - reassign     # Поиск переопределения переменных
    - unconvert    # Лишние приведения типов
      
issues:
  exclude-use-default: false # Не использовать стандартные исключения
  max-issues-per-linter: 0   # Показать все ошибки
  max-same-issues: 0         # Показать все похожие ошибки
  exclude-rules:
    - path: _test\.go
      linters:
        - goconst    # Игнорировать дублирование строк в тестах
```

Но здесь стоит быть довольно осмотрительным. Порой к линтерам начинают относиться слишком религиозно, стараясь получить идеальный код

Что точно плохой подход при работе с линтерами:

- Включать все линтеры подряд.
- Получать сотни предупреждений и гасить их (делать невидимыми для линтера) через директиву `//nolint`.
- Начинать чинить линтером код, а не улучшать его.

Вместо этого всё-таки стоит действовать немного иначе

> [!NOTE]
> Линтеры - это ещё один гарант качества кода в 95% компаний, так что стоит научиться жить и работать с ними.

3. **Проверка зависимостей**  - `govulncheck`
	Проверяет используемые в проекте зависимости на предмет известных уязвимостей:

```
govulncheck ./...
```

### Чеклист перед PR

Перед отправкой на ревью стоит выполнить небольшой список программ:

```
gofmt -w .
go vet ./...
golangci-lint run
go test ./...
go test -race ./...
govulncheck ./...
```

Это позволит убедиться, что с точки зрения написанного кода к тебе не подкопаться.

#### Названия методов и функций
В Go есть важное правило: **избегай повторения наименования пакета в его сущностях**

```
package db

func CreateDbConnection() (*DbConn, error) {}
```

Здесь плохо сразу всё:
- При вызове функции придется писать где-то следующее: `db.CreateDbConnection()`
- Возврат сущности подключения к базе в виде db.DbConn

```
package db

type Conn struct {}

func CreateConn() (*Conn, error) {}

--------------------------------

// Где-то в другом пакете

c, err := db.CreateConn()

func Do(c *db.Conn) {}
```

Теперь всё невероятно читаемо: видим, что есть пакет, который уже говорит о том, кто он и за что отвечает

```
type User struct {
  Id int
  Address string
}

func (u User) GetAddress() string {
  return u.Address
}

func (u User) Address() string {
  return u.Address
}
```

#### Еще раз об интерфейсах

Для чего нужны интерфейсы? Для того чтобы использовать только поведение, описанное в контракте интерфейса, тем самым скрывая того, кто реализует данный функционал. Это бывает полезно, когда ты создаёшь нечто универсальное, чему нужно лишь описанное в сигнатуре поведение.

```
type Formatter interface {
	Format() string
}

func StringFromSrc(src Formatter) string {
	return stc.Format()
}
```

Нам здесь правда не важно, какой именно тип реализует интерфейс. Мы создали обобщённую функцию, которую теперь можем вызвать где угодно, получив ожидаемый результат. Кстати, заметь, что интерфейсы принято называть существительным. Если интерфейс имеет единственный метод, то его называют по его именованию: `Reader`, `Writer`, `Seeker` и так далее.

Интерфейсы лучше всего объявлять в том месте, где его планируется использовать

```
package format

type Formatter interface {
  Format() string
}

type Service struct {}

func NewService() *Service {
  return &Service{}
}

func (s *Service) Format() string {}

-------------------
// Где-то в другом пакете будет не важно, что мы используем: метод напрямую или интерфейс. Мы все равно притянем пакет format

package example

import github.com/..../format

func example(f format.Formatter) {
  svc := format.NewService()
  svc.Format()
  
  f.Format()
}

-------------------

// Лучше всё-таки вынести интерфейс в место использования. Так не получим лишних импортов и полностью абстрагируем логику

package example

type Formatter interface {
  Format() string
}

func example(f Formatter) {
  f.Format()
}
```

#### nil мапы и слайсы

Встроенная функция `len()` спокойно может работать с неинициализированными сущностями, просто возвращая 0. Таким образом, вместо двух проверок на `nil` и пустоту, мы можем ограничиться только одной - через `len()`

```
func AnyDo() { // Проверки дают одинаковый результат
  var sl []int
  
  if len(sl) == 0 {
    return
  }
  
  if sl == nil {
    return
  }
  ...
}
```

Хорошим тоном считается инициализировать слайсы именно через `var`, а не `sl := \[]int{}`

#### Работа с горутинами

- Когда ты запускаешь горутину, нужно сразу же понять, где и при каких обстоятельствах она закроется.
- Если без горутины можно обойтись, лучше так и сделать.

**Второе правило** говорит о том, как всё-таки сообщество (и разработчики языка) не доверяет горутинам в продакшене и старается избегать их случайного и зачастую сложно тестируемого поведения.


#### Параметры функций

Бывает, что сталкиваемся с такой ситуацией:

```
`func Example(one int, two string, three uint, four, five uuid.UUID, six any, seven string, eightbool) (map[int]string, uint, []int, any, error) {}`
```

В подобных случаях используй структуры для возврата сложных ответов:

```
type ExampleRequest struct {
  one int
  two string
  three uint
  four, five uuid.UUID
  six any
  seven string
  eight bool
}

type ExampleResp struct {...}

func Example(req ExampleRequest) (ExampleResp, error) {}
```

#### Ошибки и паники

Кратко: **всегда обрабатывай ошибки и добавляй в них контекст**, если того требует ситуация

И конечно, **не паникуй без необходимости**. Лучше отдать ошибку, чем уронить сервис


#### Дженерики

Тут тоже кратко: **не используй дженерики только потому, что кажется, что твой алгоритм универсальный и пригодится в будущем**. Когда пригодится, тогда и стоит об этом задумываться
