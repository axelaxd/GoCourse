**Контекст** - это еще одна изюминка Go, которая помогает дирижировать программами, имеющими множество горутин

Позволяет делать в коде три важные вещи:
- Передавать сигнал отмены между горутинами;
- Управлять дедлайнами для выполнения блоков кода;
- Нести в себе метаданные сквозь все слои кодовой базы.

```
type Context interface {

	// Возвращает время, в которое контекст должен быть отменен + флаг, который говорит, установлен ли дедйлайн или нет
	Deadline() (deadline time.Time, ok bool)
	
	// Возвращает канал, который закрывается при отмене контекста
	Done() <- chan struct{}
	
	// Возвращает ошибку как причину отмены контекста
	Err() error
	
	// Позволяет получить значение из контекста по ключу
	Value(key interface{}) interface{}
}
```

То есть контекст как некоторая сущность **связан со временем**, а также с **сигналами окончания** некоторого действия

#### Типы контекста - **ctx**
1. **ctx := context.Background** - создаёт пустой контекст;

2. **ctx := context.TODO()** - тоже создает пустой контекст, но используемый в тех случаях, когда мы еще не уверены, а нужен ли он нам тут

❗ И тут же два главных правила:
- **Background-контекст** - начальный, на основе которого мы можем **выстраивать целые цепочки** из контекстов

- **TODO** **нельзя использовать в продакшене**. Никогда. Этот контекст - заглушка, которая **просто помогает** нам разрабатывать сервисы и помечать места, в которые мы хотим подставлять другие контексты

3. **ctx, cancel := context.WithCancel(ctx)** - возвращает два параметра: **контекст и функцию отмены**, связанную с ним.

	Эту функцию можно вызвать в любом участке кода и контекст в таком случае отменится, закрывая канал `Done`

4. **ctx, cancel := context.WithTimeout(ctx, 5\*time.Second)** -  возвращает контекст, который **автоматом закрывается** (и закрывает `Done`) спустя заданное время.

5. **ctx, cancel := context.WithDeadline(ctx, time.Now().Add(10\*time.Minute))** - возвращает контекст, который **закрывается после достижения конкретного времени** (14:14 МСК)

**Из дополнительных** возможностей можно использовать функцию `context.AfterFunc(ctx, func() {})`, которая выполнит переданное ей замыкание **после завершения контекста**

Также существуют методы с постфиксом `Cause`, которые позволяют добавлять бизнес-причину вызова `cancel`:

```
ctx, cancel := context.WithCancelCause(context.Background())

go func() {
	time.Sleep(200 * time.Millisecond)
	cancel(errors.New("client closed browser tab"))
}()

<-ctx.Done()
fmt.Println("Err:", ctx.Err())              // context canceled
fmt.Println("Cause:", context.Cause(ctx))   // client closed ...
```

#### Иерархии контекстов

**Прелесть контекстов заключается в том**, что из них можно создавать целые иерархии, тем самым **дробя выполнение кода** через продолжительность операций

```
ctx := context.Background()

ctx, cancel1 := context.WithCancel(ctx)

ctx, cancel2 := context.WithTimeout(ctx, 5*time.Second)
```

**Второе правило работы с контекстом**: если отменился родительский контекст, то отменяются дочерние; если отменился дочерний, то родительский не отменяется

#### Передача значений в контексте
Да, контекст может быть некоторым контейнером, в котором мы можем передавать данные меду слоями кода, от сервиса к сервису.
Пример:
	**ctx := context.WithValue(ctx, key, value)**

❗ Но никогда не передавай. в контексте параметры для выполнения бизнес логики! 

Если вдруг действительно что-то надо передать в контексте (метаданные), то хорошим тоном является объявление ключа кастомным типом в виде константы:

```
type context string // кастомный тип

const userIDKey contextKey = "userID"

ctx := context.WithValue(context.Background(), userIDKey, 123)
```

#### Работа с контекстом

```
package main

import (
    "context"
    "fmt"
    "time"
)

func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("Worker %d: остановка, причина: %v\n", id, ctx.Err())
            return
        default:
            fmt.Printf("Worker %d: работает...\n", id)
            time.Sleep(500 * time.Millisecond)
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    
    // Запускаем несколько горутин
    for i := 1; i <= 3; i++ {
        go worker(ctx, i)
    }
    
    // Даем им поработать две секунды
    time.Sleep(2 * time.Second)
    
    // Отменяем контекст
    fmt.Println("main: отправляем сигнал отмены...")
    cancel()
    
    // Даём время на завершение
    time.Sleep(1 * time.Second)
    fmt.Println("main: программа завершена")
}
```

Что происходит?
1. На основе базового контекста (`Background`) **создаётся контекст с явной отменой**
2. Далее **запускаются три горутины**, в которые происходит передача контекста для управления их жизненным циклом
3. Внутри горутин-воркеров в бесконечном цикле происходит **прослушивание канала** `Done` у контекста.

	Сначала `select` пытается понять, закрыт ли канал через `case`. Если еще не закрыт, то выполняет блок `default` и так до того момента, пока не последует сигнал от контекста

4. Код некоторое время ждёт, **имитируя бурную деятельность воркеров**, а затем явно вызывает `cancel`, после чего все воркеры получают сигнал о том, что контекст завершен через канал `Done`

❗ Для контекстов с отменой (с функцией `cancel`), **эту функцию надо вызывать всегда - зачастую через** `defer`. 

Это делается для гарантии завершения контекста в любой ситуации

```
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
```

Также мы можем явно проверять ошибки из пакета `context` через вызов:

```
if err := ctx.Err(); err != nil {
	if errors.Is(err, context.Canceled) {
		// ...
	}
	
	if errors.Is(err, context.DeadlineExceeded) {
		// ...
	}
}
```

`context.Canceled` и `context.DeadlineExceeded` - **ошибки**, которые порой **можно и нужно проверять**

#### Идиоматика  при работе с контекстом

1. Передавать контекст надо всегда первым параметром в функции. Это единый стандарт, при котором сразу видно, что функция может уметь в отмену или временное ограничение.

2. Контекст не надо хранить в структурах, так как они не имеют отношения к жизненному циклу функций и времени выполнения кода.

3. В долгих операциях надо проверять контекст через закрытие канала `Done` в `select` с неблокирующим вызовом `default`.

4. Надо внимательно следить за тайм-аутами. Если дочерний контекст будет иметь больший тайм-аут, чем родительский, то это может повлиять на некорректное поведение цепочки вызовов.

5. Использовать `context.TODO` в рабочем коде не нужно. Контекст ничего не делает, и его существование — причина отвлечения от того, что на самом деле делает код.

6. `context.Background` создаётся только на верхнем уровне вызовов. Не прерывай цепочку контекстов вновь созданным контекстом.

#### Graceful shutdown
1. **Корректно завершить работу** - **graceful shutdown**
	Что происходит, когда мы нажимаем Ctrl + C во время выполнения программы? Она мгновенно завершается. Но что если нам необходимо завершиться не сразу?
 
	**Graceful shutdown** - это способность приложения корректно завершать работу, сохраняя целостность данных и не прерывая критические операции

Как реализовать такое поведение? OC, Docker, Kubernetes общаются с нашими программами посредством.

в Go слушать эти сигналы можно при помощи пакета `os/signal`. Какие основные сигналы можно ловить:

* **SIGINT (2)** - сигнал прерывание. Обычно при нажатии Ctrl + C

- **SIGTERM (15)** - сигнал завершения. Это "вежливый" запрос на завершение, который дает приложению время на "уборку"

- **SIGKILL (9)** - сигнал принудительного завершения. Не может быть перехвачен или проигнорирован

- **SIGHUP (1)** - сигнал "повесить трубу". Сегодня часто используется для перезагрузки конфигурации

Корректное завершение программ использует каналы:
```
package main
import (
    "fmt"
    "log"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    // Создаём канал для приёма сигналов. Почему буферизированный?
    sigChan := make(chan os.Signal, 1)
    
    // Указываем, какие сигналы мы хотим получать и куда писать
    signal.Notify(sigChan,
        syscall.SIGINT,  // Ctrl+C
        syscall.SIGTERM, // Сигнал завершения
        syscall.SIGHUP,  // Сигнал перезапуска конфигурации
    )
    
    fmt.Println("Приложение запущено. Ожидаю сигналы...")
    
    // Запускаем фоновую работу
    go func() {
        for i := 1; i <= 10; i++ {
            fmt.Printf("Выполняю работу %d/10...\n", i)
            time.Sleep(2 * time.Second)
        }
    }()
    
    // Блокируемся до получения сигнала
    sig := <-sigChan
    log.Printf("Получен сигнал: %v (%v)\n", sig, sig)
}
```

Ниже показан **пример правильного** `graceful shutdown` для http-сервера

```
func gracefulServer() {
    server := &http.Server{
        Addr:    ":8080",
        Handler: createRouter(),
    }
    
    // Запускаем сервер в горутине
    go func() {
        if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Printf("Ошибка сервера: %v", err)
        }
    }()
    
    // Ждём сигнала
    sig := make(chan os.Signal, 1)
    signal.Notify(sig, syscall.SIGINT, syscall.SIGTERM)
    <-sig
    
    log.Println("Получен сигнал завершения, начинаем graceful shutdown...")
    
    // Создаём контекст с тайм-аутом для shutdown
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    
    // Корректно завершаем работу
    if err := server.Shutdown(ctx); err != nil {
        log.Printf("Ошибка при shutdown: %v", err)
        server.Close() // Вынужденное завершение
    }
    
    log.Println("Сервер корректно завершён")
}
```


#### Примитивы синхронизации
Для того чтобы **асинхронный, многопоточный код выполнялся,** необходимо синхронизировать разные его ветви между собой. Или же защитить данные от множественного доступа.

Каналы - это пример **примитивов синхронизации**. 

В дополнение, в Golang примитивы синхронизации (помимо каналов), лежат в двух пакетах: `sync` и `atomic` (внутри `sync`). Пройдемся по ним и постараемся понять, с чем мы можем иметь дело и когда.

1. **Атомики** - **atomic**
	**Позволяют получить доступ к переменной с гарантией**, что ни одна другая горутина в момент доступа не владеет ею: ни читает значение, ни пишет новое

	То есть атомарные операции **гарантированно выполняются без прерываний** и обеспечивают синхронизацию доступа к данным на уровне инструкций процессора.

```
func main() {
    var v int64 = 0
    
    go atomic.AddInt64(&v, 1) // 1
    go atomic.AddInt64(&v, -2) // 1 + (-2)
    
    time.Sleep(1 * time.Second)
    
    val := atomic.LoadInt64(&v)
    fmt.Println(val) // -1
}
```

В этом примере мы без гарантии порядка выполнения горутин, имеем гарантию, что всегда получим корректный и потокобезопасный результат

2. **Мьютексы** - **Mutex**
	Позволяет защищать блок кода от неконсистентных данных при доступе к ним из нескольких горутин

Например, одна горутина пишет в мапу, а потом, спустя время, читает из неё, надеясь получить в одной операции те данные, что уже были сложены в мапу

А в этот момент друга горутина получит доступ к этой мапе и перепишет значение, то получится неожидаемое поведение, которое сломает нашу логику

	Поэтому мьютексы очень часто защищают большие блоки кода от конкурентного доступа. В том числе в связки с мапами, делая их потокобезопасными

**Как работает:**
	При вызове мьютекса он блокирует участок кода для текущей горутины, не давая другим горутинам выполнять его. 
	
Зачастую горутины определяются в структурах для того, чтобы использоваться в связанных с ними методах. Но мы можем вызвать мьютекс напрямую:

```
func exampleOne() {
	mu := sync.Mutex{}
	
	mu.Lock()
	fmt.Println("Mutex locked")
	mu.Unlock()
}
```

Вызывая `Lock` и `Unlock` мы заблокировали участок кода для других горутин. Причем операции чтения и записи.

Но всё же в структурах с мапами мьютексы используются чаще. Здесь стоит сказать о важном: **поле с мьютексом располагается в блоке над объектом, который он защищает**.

```
type Cache struct {
	// Мы показываем, что мьютекс защищает мапу
	mu sync.Mutex
	m map[int]int

	sl []int // Никто не мешает вызывать, но слайс не под защитой мьютекcа
}

func (c *Cache) Add(key int, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()

	c.m[key] = val
}
```

**Про RW-мьютекс**:
	Но помимо обычного мьютекса в Go существует **RW-мьютекс**, который имеет методы `Rlock` и `RUnlock`, позволяющие не блокировать горутины с операциями чтения 

Но в случае появления горутины, которая намерена мутировать данные, мьютекс заблокирует код для всех прочих горутин, даже тех, кто пришёл читать данные


3. **Вейтгруп** - **WaitGroup**
	Позволяет ожидать выполнения конечного, заранее известного числа горутин. Имеет всего три метода:

- `Add(n)` - добавляет в счётчик ожидания горутин их общее количество
- `Done()` - производит декремент счётчика горутин по окончании одной из них
- `Wait()` - блокирует выполнение программы для ожидания окончания работы всех n горутин

```
func main() {
	var wg sync.WaitGroup

	wg.Add(2)

	for range 2 {
		go func() {
			defer wg.Done()

			fmt.Println("Hello world")
		}()
	}

	wg.Wait()
}
```

В примере выше мы создаем счётчик через **waitGroup**; запускаем именно столько горутин, сколько у нас их в счётчике (иначе можем попасть на deadlock);

В `defer` сбрасываем счётчик (каждый раз -1) - можно вызывать `Done()` и не в `defer`, но использование этого слова - гарантия срабатывания;

Дальше блокируем горутину `main`, пока все дочерние горутины не отработают.

Вывод:
	**WaitGroup** - невероятно полезный инструмент при работе с пулом горутин. Однако есть недостаток - обработка ошибок превращается в головную боль.

В случае возникновения подобных проблем стоит воспользоваться пакетом `errGroup`, который помогает отслеживать возникновение ошибок и корректно завершать горутины

4. **Once**
	Позволяет гарантировать, что некоторая функция, доступ к которой имеется у множества горутин, выполнится **только один раз** самой первой горутиной

```
var (
    once sync.Once
)

func initialize() {
    fmt.Println("Инициализация ресурсов (выполняется один раз)...")
    
}
func main() {
    var wg sync.WaitGroup
    
    // Запускаем 10 горутин, которые хотят выполнить инициализацию
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
			
            once.Do(initialize) 
            fmt.Printf("Горутина %d завершила работу\n", id)
        }(i)
    }
    
    wg.Wait()
    
    fmt.Println("Программа завершена.")
}
```

5. **sync.Map**
	Довольно медленная и неуклюжая мапа, лучше не использовать


## Дополнительно: concurrency patterns

#### Паттерны конкурентности 
1. `Singleflight` позволяет в случае запроса к какому-то сервису или части бизнес-логики группировать запросы, **ожидающие одной и той же долгой операции**
```
// call — структура, которая описывает вызовы некоторой функции. Содержит поля с ошибкой и значением, которые мы пошарим на весь пул запросов, а также канал, закрывающийся при окончании работы запроса/функции

type call struct {
    err   error
    value any
    done  chan struct{}
}

// SingleFlight реализует логику паттерна, используя список вызовов в мапе по конкретным ключам, чтобы группировать вызовы, относящиеся к одному и тому же ресурсу, друг с другом. В мапе вызов хранится указателем, чтобы имелась возможность разделять этот объект между разными горутинами

type SingleFlight struct {
    mutex sync.Mutex
    calls map[string]*call
}

func NewSingleFlight() *SingleFlight {
    return &SingleFlight{
        calls: make(map[string]*call),
    }
}


// Do реализует действие вычисления некоторой функции action
func (s *SingleFlight) Do(ctx context.Context, key string, action func(context.Context) (any, error)) (any, error) {

    // Большой блок под мьютексом, в котором его закрытие происходит дважды, так как defer тут не поможет программе завершиться корректно - после второго Unlock у нас происходит выполнение функции, которая с defer s.mutex.Unlock просто заблокирует этот код на всё время своей работы
    // Здесь мы проверяем существование вызова, и если он есть, то просто вешаем его в ожидание через мапу. Иначе создаём новый вызов
    
    s.mutex.Lock()
    
    if call, found := s.calls[key]; found {
        s.mutex.Unlock()
        return s.wait(ctx, call)
    }
    
    call := &call{
        done: make(chan struct{}),
    }
    
    s.calls[key] = call
    s.mutex.Unlock()
    
    // Запускаем функцию в горутине, чтобы реализовать ожидание данных и их получение через разделяемую структуру вызова call. В случае паники мы её обрабатываем, не роняя программу, просто подчищая за собой в списке вызовов
    
    go func() {
        defer func() {
            if v := recover(); v != nil {
                call.err = errors.New("error from single flight")
            }
            close(call.done)
            
            s.mutex.Lock()
            delete(s.calls, key)
            s.mutex.Unlock()
		}()
		
        call.value, call.err = action(ctx)
    }()
    
    return s.wait(ctx, call)
}

// wait ожидает либо завершения контекста для всего запроса, чтобы завершить все запросы, либо сигнала от лидерского запроса, что он завершился и поделился данными с ожидающими вызовами

func (s *SingleFlight) wait(ctx context.Context, call *call) (any, error) {
    select {
    case <-ctx.Done():
        return nil, ctx.Err()
    case <-call.done:
        return call.value, call.err
    }
}
```

2. ``Генератор``
	Используется, когда необходимо создать некоторое количество данных, поделиться ими с другой горутиной, а затем закрыть канал

```
func generator() <- chan int {
	ch := make(chan int)
	
	go func() {
		for i := range 10 {
			ch <- i + 1
		}
		close(ch)
	}()
	
	return ch
}
```

3. `Fan-in` 
	Помогает собирать данные из нескольких каналов в один общий.
	
	Подходит для случаев объединения результатов расчёта от нескольких горутин в единой точке сбора данных

```
func fanIn(input1, input2 <-chan string) <-chan string {
    ch := make(chan string)
    
    go func(){
        for {
            select {
                case s := <-input1: 
                    ch <- s
				case s := <-input2: 
                    ch <- s
            }
        }
    }()
    
    return ch
}
```

4. `Fan-out`
	Распределяет данные из одного канала в несколько.
	
	Полезно, например, использовать в связке с генератором данных:

```
func worker(ch <- chan int, wg *sync.WaitGroup) {
	defer wg.Done()
	
	for v := range ch {
		fmt.Println(v)
		time.Sleep(1 * time.Second)
	}
}

func sender() {
	ch := make(chan int, 2)
	var wg sync.WaitGroup
	
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go worker(ch, &wg)
	}
	
	for i := range 10 {
		ch <- i
	}
	
	close(ch)
	
	wg.Wait()
	fmt.Println("done")
}

func main() {
	sender()
}
```

5. `Pipeline`
	Выстраивает цепочку обработки данных, что необходимо в случае запуска некого конвейера для, например, последовательной обработки файлов:

```
func producer() <-chan int {  
    c := make(chan int)  
  
    go func() {  
       for i := range 10 {  
          c <- i + 1  
       }  
       close(c)  
    }()  
  
    return c  
}  
  
func producerConsumer(c <-chan int) <-chan int {  
    out := make(chan int)  
  
    go func() {  
       for v := range c {  
          out <- v * 2  
       }  
       close(out)  
    }()  
  
    return out  
}  
  
func consumer(ch <-chan int) {  
    for v := range ch {  
       fmt.Println(v)  
    }  
}
```

6. `Worker pool`
	Паттерн, помогающий организовать работу над данными в виде параллельных воркеров. 
	
	Обычно используются при большом кол-ве однотипной работы над крупными данными:

```
func worker(jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {  
    defer wg.Done()  
  
    for j := range jobs {  
       time.Sleep(1 * time.Second)  
       fmt.Println("job", j)  
       results <- j * j  
    }  
  
}  
  
func main() {  
    jobs := make(chan int)  
    results := make(chan int)  
  
    var wg sync.WaitGroup  
  
    for i := range 3 {  
       wg.Add(1)  
       go worker(jobs, results, &wg)  
    }  
  
    go func() {  
       for i := range 10 {  
          jobs <- i  
       }  
       close(jobs)  
    }()  
  
    go func() {  
       wg.Wait()  
       close(results)  
    }()  
  
    for result := range results {  
       fmt.Println(result)  
    }  
}
```
