## Ответы на вопросы

### Почему `error` --- обычное значение?

`error` --- встроенный интерфейс с методом `Error() string`. Ошибки
возвращаются, сохраняются, сравниваются и оборачиваются как обычные
значения, поэтому контроль ошибок остаётся явной частью потока
программы.

### Как оборачивать ошибку и зачем `%w`?

`fmt.Errorf("load user: %w", err)` добавляет контекст и сохраняет
исходную ошибку в цепочке. `%w` нужен, чтобы затем
`errors.Is`/`errors.As` могли пройти по этой цепочке. `%v` только
форматирует текст и не создаёт unwrap-связь.

### Чем `errors.Is` отличается от `errors.As`?

`errors.Is(err, target)` отвечает, соответствует ли ошибка конкретной
целевой ошибке, проходя цепочку wrapping. `errors.As(err, &target)` ищет
в цепочке ошибку подходящего **типа** и записывает её в target.

### Когда выполняется `defer`?

Отложенные вызовы выполняются при выходе из окружающей функции --- при
обычном `return` и во время раскрутки стека из-за `panic`. Несколько
defer в одной функции выполняются в обратном порядке, LIFO. Аргументы
обычного deferred-вызова вычисляются в момент выполнения оператора
`defer`.

### Чем `panic` отличается от обычной ошибки?

`error` предназначен для ожидаемых проблем, которые вызывающий код может
обработать. `panic` прерывает нормальный поток и начинает раскрутку
стека; обычно его оставляют для действительно аварийных ситуаций,
нарушенных инвариантов или ошибок программирования, а не для обычной
бизнес-ошибки.

### Как работает `recover` и где его уместно использовать?

`recover` может остановить текущую панику, если вызван **непосредственно
из deferred-функции** во время раскрутки стека. Его уместно ставить на
контролируемой границе, например чтобы один упавший HTTP-request не
уронил весь процесс, залогировать panic и вернуть 500. Использовать
`recover` как замену обычной обработке `error` не стоит.

### Ошибки

Ошибки - это не просто условия для поверки, а **значения**, которые
имеют свой тип, с которыми можно работать так же, как и с любыми другими
данными

    _, err := fmt.Scan(&x)

    if err != nil {
        fmt.Println(err)
    }

Самое важное, что мы должны всегда помнить: **обрабатывать ошибки нужно
всегда**

Итак, что такое ошибка в Go? Это значение. Но ещё это **интерфейс**!

    type error interface {
        Error() string
    }

То есть всякий тип, который удовлетворяет этому интерфейсу, может быть
ошибкой. А значит с ошибками можно работать по-разному:

**Во-первых**, можно добавлять ошибке контекст, Добавив такие параметры,
как:

-   параметры функции;
-   значения переменных;
-   дополнительные сообщения об ошибках;

Одним из способов обогатить ошибку является использование пакета `fmt`.
Функция `Errorf` добавляет форматированное описание функции:

    return fmt.Error("Ошибка при обработке юзера %s: %w", UserID, err)

Тут мы уже существующей ошибке `err` **добавляем уровень контекста**.
`%w` - этот глагол форматирования позволяет в дальнейшем извлечь
**исходное сообщение** об ошибке

**Во-вторых**, раз мы можем оборачивать ошибки, то можем и раскрывать
их. Для этого используется пакет стандартной библиотеки `errors`. А
именно метод `errors.Is`

    if err != nil && errors.Is(err, "какая-то ошибка"){
        fmt.Println("тут ошибка")
    }

Метод позволяет отыскать в цепочке ошибок **ту самую** нужную.

**В-третьих**, можно создавать ошибки. Делается это просто, через тот же
пакет `errors`:

    var ErrInvalidArgument = errors.New("Invalid argument")

    func checkArgument(a int) error {
        if a == 0 {
            return ErrInvalidArgument
        }
        
        return nil
    }

Важно еще и то, что подобные sentinel-ошибки **должны начинаться** с
префикса `Err...` или `err...` при объявлении

**В-четвертых**, раз наши ошибки могут быть любым типом,
удовлетворяющему интерфейсу `Error`, можно проверять существование
конкретного типа у ошибки через метод `error.As`:

    type MyError struct {
        Code int
        Msg  string
    }

    func (e *MyError) Error() string {
        return fmt.Sprintf("Ошибка %d: %s", e.Code, e.Msg)
    }

    func doSomething() error {
        return fmt.Errorf("дело дрянь: %w", &MyError{Code: 500, Msg: "Сервер недоступен"})
    }

    func main() {
        var targetErr *MyError
        
        err := doSomething()
        if errors.As(err, &targetErr) {
            fmt.Println("Код ошибки:", targetErr.Code, "Сообщение:", targetErr.Msg)
        } else {
            fmt.Println("Произошла неизвестная ошибка")
        }
    }

В новой версии языка 1.26 подобный синтаксис упростили:

    pathError, ok := errors.AsType[*fs.PathError](err)

3.  **Отложенные вызовы** - **defer** Позволяет отложить выполнение
    функций, пока не завершится выполнение функции, в чьём теле они
    существуют.

    Можно, например, писать о закрытии соединения рядом с его открытием.

В теле любой функции можно вызвать неограниченное кол-во `defer`. Они
будут выполняться по принципу `LIFO` - последним пришел, первым ушел

    func Example() {
        for i := 3; i > 0; i-- {
            defer fmt.Print(i, " ") 
            // Используем существующую функцию + выведется ответ, обратный объявлению, то есть `1 2 3`
        }
    }

    func Example3() {
        for i := 3; i > 0; i-- {
            defer func(n int) {    // Анонимная функция
                fmt.Print(n, " ")
            }(i)
        }
    }

Использование `defer`, по сути, гарантирует, что в случае возникновения
ошибок, мы в любом случае выполним код, который есть у `defer` (несмотря
на ошибки)

4.  **Паники не ошибки** - **panic** В Go есть аналоги необрабатываемых
    исключений из других языков. И это "паника", которая вызывается
    через `panic()`

    По сути, это фатальная ошибка в коде, приложение падает, выдавая в
    стандартный вывод ошибок стек вызова с **описанием местоположения**
    паники.

5.  **Ловец паник** - **recover** Паники можно перехватить, обработать и
    продолжить выполнение программы как ни в чем не бывало.

    И это можно сделать с помощью функции `recover()`вместе с `defer`

    `recover` работает, только если она вызывается внутри `defer`. Иначе
    функция просто возвращает значение, переданное в `panic`

```{=html}
<!-- -->
```
    package main

    import (
        "fmt"
    )

    func Example() {
        fmt.Println("Inside function")
        defer func() {
            if r := recover(); r != nil {
                fmt.Println("Recovered:", r)
            }
        }()
        panic("Panic!")
    }

    func main() {
        Example()
        fmt.Println("Main function continues")
    }

Вывод тут будет следующим:

    Inside function
    Recovered: Panic!
    Main function continues

## Идиоматика из tooling-конспекта

#### Ошибки и паники

Кратко: **всегда обрабатывай ошибки и добавляй в них контекст**, если
того требует ситуация

И конечно, **не паникуй без необходимости**. Лучше отдать ошибку, чем
уронить сервис

#### Дженерики

Тут тоже кратко: **не используй дженерики только потому, что кажется,
что твой алгоритм универсальный и пригодится в будущем**. Когда
пригодится, тогда и стоит об этом задумываться
