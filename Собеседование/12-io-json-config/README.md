## Ответы на вопросы

### Чем `os.Open` отличается от `os.OpenFile`?

`os.Open(name)` --- удобная обёртка для открытия файла на чтение.
`os.OpenFile` позволяет явно задать флаги (`O_RDONLY`, `O_RDWR`,
`O_CREATE`, `O_APPEND` и т.д.) и permissions при создании файла.

### Зачем закрывать файл через `Close`?

Открытый файл использует системный ресурс --- file descriptor/handle.
`Close` освобождает его и завершает работу с ресурсом; при записи ошибка
`Close` тоже может быть значимой, поэтому в критичном коде её не всегда
стоит игнорировать.

### Когда `os.ReadFile` плохой выбор?

Когда файл может быть большим или данные удобнее обрабатывать потоково:
`ReadFile` читает содержимое целиком в память. Для больших данных лучше
`io.Reader`, `bufio.Reader`/`Scanner` или декодер, работающий с потоком.

### Что такое `io.Reader` и `io.Writer`?

Это маленькие интерфейсы стандартной библиотеки. `Reader` имеет
`Read(p []byte) (n int, err error)`, `Writer` ---
`Write(p []byte) (n int, err error)`. Благодаря им один алгоритм может
работать с файлами, сетью, buffers и другими источниками/приёмниками.

### Зачем `bufio`?

Он добавляет буферизацию поверх `io.Reader`/`Writer`, уменьшая число
мелких системных/нижнеуровневых операций и предоставляя удобные способы
чтения, например `Scanner` для токенизированного текста.

### Чем Marshal отличается от Unmarshal?

`json.Marshal(v)` кодирует Go-значение в JSON и возвращает `[]byte`.
`json.Unmarshal(data, &v)` декодирует JSON в Go-значение; нужен
указатель, чтобы функция могла записать результат.

### Как работают struct tags и `omitempty`?

Tag вроде `json:"user_id,omitempty"` задаёт имя JSON-поля и опции
кодирования. `omitempty` пропускает поле, если оно считается пустым по
правилам `encoding/json`. `json:"-"` полностью исключает поле.

### Когда JSON удобнее YAML?

JSON особенно удобен для API, машинного обмена и строгой экосистемы
стандартного `encoding/json`. YAML часто удобнее человеку для
конфигураций и комментариев, но его синтаксис сложнее и требует внешней
библиотеки в Go.

2.  **Открытие файла** - **os.Open()** и **os.OpenFile()**
    **os.Open()** - открываем файл **только для чтения**, и если такого
    файла не существует в директории, то вернётся ошибка типа
    `type PathError = fs.PathError`

```{=html}
<!-- -->
```
    file, err := os.Open("input.txt")
    if err != nil {
        return err
    }

    defer file.Close()

Однако правильнее вызывать закрытие всё же с обработкой ошибки:

    defer func() {
        if err := file.Close(); err != nil {
            fmt.Println(err)
        }
    }

**os.OpenFile()** **os.OpenFile()** - можно открыть файл и для чтения, и
для записи, и создавая его перед использованием. Для этого надо
использовать **определённые флаги** вторым аргументом (также уровни
доступа)

    file, err := os.OpenFile("notes.txt", os.O_RDWR|os.O_Create, 0644)
    if err != nil {
        log.Fatal(err)
    }

    if err := file.Close(); err != nil {
        log.Fatal(err)
    }

**Дальнейшее чтение** с помощью переменной `file` можно осуществлять
через метод `Read`, который позволяет читать конкретное кол-во байтов в
переданный в качестве аргумента слайс

    b := make([]byte, 1024)

    for {
        n, err := file.Read(b) // Возвращает кол-во прочитанных байтов
        if err != nil {
            if errors.Is(err, io.EOF) {
                return nil
            }
            
            return fmt.Errorf("Warning: %w", err)
        }
    }

4.  **Создать файл** - **os.Create()** io.EOF - сигнализирует о конце

```{=html}
<!-- -->
```

        defer file.Close()
        var buffer = make([]byte, 4096) // Буфер размером 4 КБ

        }

5.  **Проверить, есть ли файл в директории** - **os.Stat** +

```{=html}
<!-- -->
```
    func fileExists(filename string) (bool, error) {
        _, err := os.Stat(filename)
        if err == nil {
            return true, nil
        }
        
        if errors.Is(err, fs.ErrNotExist) {
            return false, nil
        }
        
        return false, err
    }

8.  **Основные правила для работы с файлами и куда вставлять append,
    create, write**

-   **os.O_APPEND\|os.O_WRONLY** - всегда добавит в конец

#### Пакет io

-   `io.Reader` --- описывает типы, читающие данные
    методом `Read(p []byte) (int, error)`. А мы ведь его видели в
    пакете `os`!

-   `io.Writer` --- описывает типы, записывающие данные
    методом `Write(p []byte) (int, error)`.

-   `io.Closer` --- описывает типы, освобождающие ресурсы
    методом `Close() error`.

-   `io.ReadWriter` --- объединяет интерфейсы `io.Reader` и `io.Writer`.

-   `io.ReadCloser`, `WriteCloser` --- объединяют
    интерфейсы `io.Reader/io.Writer` и `io.Closer` и так далее.

#### Работа с большими файлами

9.  **Готовые решения с большими объемами данных** - **bufio** Здесь
    можно делать все: читать, писать, перезаписывать данные

    `bufio.Scanner` представляет из себя **высокоуровневый инструмент**
    для последовательного чтения данных. Чаще всего текстовых:

```{=html}
<!-- -->
```
    file, err := os.Open("input.txt")
        if err != nil {
            log.Fatal(err)
        }

        defer file.Close()

        scanner := bufio.NewScanner(file) // Создаем сканнер
        for scanner.Scan() { // Здесь мы его читаем
            fmt.Println(scanner.Text()) // Текст
        }

        if err := scanner.Err(); err != nil {
            log.Fatalf("Ошибка чтения: %v", err)
        }

Здесь мы **получаем дескриптор файла** для чтения и передаем его в
конструктор. И далее `scanner` сам возвращаем нам построчный вывод
**разделяя поток данных** по нужным токенам (например, `\n`)

Однако в случаях длинных строк, бинарных данных и желания управлять
чтением серьезнее, лучше посмотреть в сторону
`bufio.NewReader(io.Reader)`

        return err

# JSON / YAML / configuration

**Сериализация** - процесс преобразования в формат (struct -\>
JSON/YAML, `json.Marshal`)

**Десериализация** - обратный процесс, когда из строки или файла снова
создаётся объект (JSON/YAML -\> struct, `json.Unmarshal`)

1.  **Главная библиотека** - **encoding/json** \#### YAML Более
    дружественный человеку текстовый формат сериализации данных.
    Подходит для удобного хранения конфигурации больше, чем `JSON`

```{=html}
<!-- -->
```
    server:
        port: 8080
        host: localhost
    app:
        log_level: 2
        enabled_test: true
        
    test: null
    dev: ["local", "stage", "prod"]

В отличие от `JSON` формат `YAML` поддерживает комментарии, что также
упрощает работу с ним.

    this_is_string: !!str 67.43

Объявляя тип `!![тип]`, мы даем понять, что именно ожидаем при парсинге
файла

Также `YAML` имеют возможность создавать внутри себя якоря/алиасы, тем
самым позволяя переиспользовать значения

Якоря начинаются с `&` перед неймингом:

    default: &default_settings
        port: 8080
        
    local:
        <<: *default_settings
        host: localhost

В целом формат позволяет работать с данными намного глубже и
вариативнее, чем это позволяет делать `JSON`. Именно поэтому он и
используется для конфигурационных файлов больше.

Фан-факт: ты можешь встретить файлы с двумя различными форматами
--- `.yml` и `.yaml`. Оба правильные, но предпочтительнее использовать
второй вариант

#### Теги структур

Структуры - самый качественный способ организации данных. Их поля должны
содержать определённые теги, по которым рантайм поймёт, как и куда
складывать данные из файлов.

Например:

    type Config struct {
        Port int
        Host string
    }

Эта структура вряд ли чем-то поможет. Делаем небольшое движение рукой и
получаем:

    type Config struct {
        Port int      `json:"port" yaml: "port"`
        Host string   `json:"host" yaml: "host"`
    }

Теги - это метаданные полей.

Если говорить про `JSON`, то пакет `encoding/json` по умолчанию
сериализует только **экспортируемые** поля структуры, используя имена
полей, как имя json-ключа, если тег этому полю не задан. Если поле в
структуре не экспортируемое, то и json-пакет с ним работать **не
будет**.

    type Config struct {
        Port int    `json:"port" yaml:"port"`
        host string `json:"host" yaml:"host"` // не сериализуется
    }

Но json-теги могут быть не просто именем ключа/поля. Можно управлять
сериализацией более гибко:

    type User struct {
        Name     string `json:"name"`             // Обычный кейс
        
        Surname  string `json:"last_name"`        // Разные имена
        
        Age      int    `json:"age,omitempty"`    // Дефолт имя
        
        Password string `json:"-"`                // Исключается
        
        Address  string `json:",omitempty"`       // Дефолт - пустая
        
        Phone    string `json:",string"`          // В json-строку
        
        HasJob   bool   `json:"has_job,omitzero"` //
        
        Foo      *int   `json:"foo"`              //
    }


    func main() {
        // Создаем экземпляр User
        user := User{
            Name:    "John",
            Surname: "Doe",
            Age:     30,
            Phone:   "123456",
            HasJob:  true,
            // Password не задана — она будет проигнорирована при JSON
            // Foo — nil указатель
        }
        
        // Сериализуем в JSON
        jsonData, _ := json.Marshal(user)
        fmt.Println(string(jsonData))
    }

`omitempty` - пропускает значения при создании json-объектов, если они
дефолтные для типа - `zero values`

`omitzero` - позволяет убирать именно нулевые значения для всех типов, с
которыми не мог работать `omitempty`

    response := answer{Key: "value"}

    b, err := json.Marshal(response) // Преобразуем go-объект в json-строку (байты)
    if err != nil {
        panic(err)
    }

    fmt.Println(string(b)) // {"key":"value"}
    k := answer{}

    err = json.Unmarshal(b, &k) // Обратное действие: превращение json-строки в структуру

    if err != nil {
        panic(err)
    }

#### JSON VS YAML

-   `JSON` стоит выбрать, когда нужен строгий, простой, машинный формат;
-   `YAML` требуется при наличии большого конфига и частой редактуры
    человеком.

#### Переменные окружения

Ещё одним источником конфигурации для приложений могут служить
переменные окружения. Это набор строковых пар `key=value`, хранящихся в
операционной системе вне кода программ, то есть обеспечивающих
универсальность параметров в различных средах для набора программ,
запускаемых в них.

У переменных окружения есть три сильные стороны:

-   Они легко меняются без пересборки самой программы.
-   Они не привязаны к языку или платформе.
-   Их удобно подставлять при запуске, не храня секретные данные в
    исходном коде.

2.  **Раскрыть значения переменных окружения** - **go env**

Переменные окружение можно считывать прямо из кода Go. Например, в MacOS
можно добавить свою переменную в `~/.zshrc`, записав в конец:

    export APP_PORT=":8080"

После сохранения используем команду:

    source ~/.zshrc

В мини-программе на Go можно обнаружить значение этой переменной:

    func main() {
        fmt.Println(os.Getenv("APP_PORT"))
    }

**Важно** ещё и то, что переменные окружения --- это строки. А значит,
после получения значения переменной, его стоит провалидировать и
преобразовать в нужный тип.

3.  **Про файл окружения** - **env** Существует полезная для работы
    библиотека `joho/godotenv`, которая через функцию `godotenv.Load()`
    загружает переменные из файла `.env` в саму систему, а мы через
    `os.Getenv` можем загрузить конфигурации в код

```{=html}
<!-- -->
```
    import "github.com/joho/godotenv"

    func main() {
        godotenv.Load() // Загружает переменные из .env в систему
        val := os.Getenv("MY_VAR")
    }

Но мы часто встречаемся с ситуацией, когда для одного сервиса может
существовать один-другой десяток переменных. Что делать с этим? Вызывать
на каждый чих `os.Getenv` как-то грустно.

На встречу приходит ещё одно решение в виде библиотеки `caarlos0/env` и
тегов полей структуры:

    package main

    import (
        "fmt"
        "log"
        "github.com/caarlos0/env"
        "github.com/joho/godotenv"
    )

    // Определение структуры с тегами `env`
    type Config struct {
        DBHost  string `env:"DB_HOST"`
        DBPort  int    `env:"DB_PORT"`
        APIKey  string `env:"API_KEY" envDefault:"12345678"` // умолч.
        Debug   bool   `env:"DEBUG"`
    }

    func main() {
        // Загружаем .env-файл (если он есть)
        if err := godotenv.Load(); err != nil {
            log.Println("No .env file found, relying on environment variables")
        }
        
        // Создаём экземпляр структуры
        cfg := Config{}
        
        // Парсим переменные окружения в структуру
        if err := env.Parse(&cfg); err != nil {
            log.Fatalf("Error parsing env: %v", err)
        }
        
        // Теперь переменные в структуре
        fmt.Printf("Config: %+v\n", cfg)
        fmt.Println("Database Host:", cfg.DBHost)
    }

**Заметь**, что используется специальный тег `envDefault`, который
говорит о том, что если такой переменной нет, то библиотека будет
взаимодействовать с кодом и подставлять указанное значение

Когда стоит использовать `.env`? В случае локальной разработки или в CI

#### Дефолтные значения

**Всегда** стоит предусмотреть для критичных параметров конфигурации
дефолтные значения.

В случае с `.env`, это специальный тег. При работе с флагами мы тоже
можем устанавливать значение по умолчанию:

    // Имя, дефолт значение, описание
    port := flag.Int("port", 8080, "Порт сервера")
