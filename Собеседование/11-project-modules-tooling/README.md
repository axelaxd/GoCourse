## Ответы на вопросы

### Чем package отличается от module?

Package --- единица Go-кода в одном каталоге с общим `package`. Module
--- версионируемая коллекция пакетов с корнем, определённым `go.mod`.

### Что лежит в `go.mod` и `go.sum`?

`go.mod` хранит module path, директиву версии Go и требования/замены
зависимостей. `go.sum` содержит криптографические суммы загруженных
версий модулей и их `go.mod`, помогая проверять целостность и
воспроизводимость зависимостей.

### Что означают direct и indirect dependencies?

Direct dependency импортируется кодом главного модуля напрямую. Indirect
нужна графу сборки, но не импортируется пакетами главного модуля
напрямую; в `go.mod` она может быть отмечена `// indirect`.

### Для чего `internal`, `cmd`, `pkg`?

`internal` имеет специальное значение для Go: его пакеты можно
импортировать только из разрешённого родительского дерева. `cmd` ---
распространённая convention для директорий исполняемых команд. `pkg` ---
лишь community convention для публичных библиотечных пакетов и не имеет
специальной семантики в языке.

### Почему циклические импорты запрещены?

Go требует ацикличный граф package imports. Это упрощает порядок
компиляции, инициализацию и архитектуру зависимостей; цикл `A -> B -> A`
является compile error.

### Что делают `gofmt`, `goimports`, `go vet`, `golangci-lint`, `govulncheck`?

`gofmt` приводит код к стандартному формату. `goimports` форматирует и
добавляет/удаляет imports. `go vet` ищет подозрительные конструкции.
`golangci-lint` запускает набор статических анализаторов/линтеров.
`govulncheck` проверяет известные уязвимости, релевантные зависимостям и
вызываемому коду.

### Какой чеклист прогнать перед PR?

Базово: форматирование, `go vet ./...`, `go test ./...`,
`go test -race ./...`, настроенный линтер и при необходимости
`govulncheck ./...`. Конкретный проект может добавлять integration
tests, генерацию и другие CI-проверки.

Go предлагает следующие ключевые механизмы для работы с большими
проектами:

-   **Пакеты** - механизм организации кода и управления областью
    видимости;
-   **Модули** - управление зависимостями, версиями и границами проекта

Модульная система в Go позволяет управлять зависимостями и их версиями

Пакетная структура помогает разбить проект на логические блоки, каждый
из которых моет быть независимо использован

#### Пакеты, модули и области видимости

**Пакет в Go** - это **набор файлов** с одинаковым объявлением `package`
в одном каталоге и объединенные общим пространством имен: они
компилируются вместе.

**Модуль** - **коллекция пакетов**, которая публикуется,
распространяется и версионируется как одно целое. Модуль **определяется
наличием файла** `go.mod`

1.  **Создать модуль** - **go mod init \<name\>**

Модуль может содержать в свою очередь множество пакетов:

    example.com/my-module # модуль, представляющий собой программу
    ├── go.mod
    ├── cmd/        # пакет с точкой входа в программу
    │   └── app/
    │       └── main.go # точка входа в программу
    ├── internal/   # пакеты, доступные только внутри этого модуля/программы
    │   ├── config/ # пакет для работы с конфигурациями
    │   └── server/ # пакет для работы с серверной логикой
    └── pkg/        # общедоступные пакеты для прочих программ и сервисов
        ├── database/
        └── logger/

#### Работа с пакетами

Каждый файл в Go должен начинаться с объявления пакета, к которому он
принадлежит

    package config

В примере выше мы подразумеваем, что создали как минимум один go-файл в
пакете `config`. Но в одном пакете может находиться много файлов

**Особый случай** - **main** Пакеты с таким объявлением служат точкой
входа для исполняемых программ и содержат функцию `main`, зачастую
пребывая в единичном экземпляре

    package main

    func main() {
           // Начало выполнения программы
    }

**Главное правило**: называть **директории и пакеты** внутри них
**одинаково**

А еще, если в директории создать хотя бы 2 go-файла с разными
наименованиями пакетов, то компилятор будет ругаться, так как **наличие
файлов с разными наименованиями пакетов внутри одной директории
запрещено!**

2.  Использование кода из других пакетов - **import**

```{=html}
<!-- -->
```
    package main
    import (
        "fmt"                        // стандартный пакет
        "my-module/internal/config"  // внутренний пакет
        "github.com/sirupsen/logrus" // внешний пакет
    )
    func main() {
        cfg, err := config.Load()
        if err != nil {
            logrus.WithError(err).Fatalln("loading config")
        }
        fmt.Printf("Config loaded: %+v\n", cfg)
    }

В случае, если требуется затянуть зависимость внешнего пакета,
используется встроенная в Go команда `go get ...`

❗При импорте пакетов, **важно знать и помнить**, что Go запрещает
циклические импорты пакетов. Например, если пакет `A` импортирует
пакет `B`, а пакет `B` импортирует пакет `A`, компилятор выдаст ошибку

#### Области видимости пакетов

-   **Экспортируемые** (видимые из других пакетов) идентификаторы
    начинаются с **заглавной буквы**;
-   **Неэкспортируемые** (видимые только внутри пакета) ---
    с **маленькой буквы**.

```{=html}
<!-- -->
```
    package user

    // Экспортированный тип (виден извне)
    type User struct {
        Name string // экспортированное поле
        age  int    // неэкспортированное поле
    }

    // Экспортированная функция
    func NewUser(name string, age int) User {
        return User{
            Name: name,
            age:  age,
        }
    }

    // Неэкспортированная функция
    func validate(u User) bool {
        return u.Name != "" && u.age > 0
    }

В этом примере мы видим ключевой принцип инкапсуляции в Go. Структура
`User` экспортирована и доступна извне пакета, но поле `age` скрыто.

    package main

    import (
        "fmt"
        "my-module/user"
    )

    func main() {
        u := user.NewUser("Alice", 30)
        
        fmt.Println(u.Name) // доступно
        
        fmt.Println(u.age)  // ошибка компиляции
        user.validate(u)    // ошибка компиляции
    }

3.  Функция **init** Каждый пакет может содержать функции `init`,
    которые выполняются на стадии инициализации пакета:

```{=html}
<!-- -->
```
    package database

    import "log"

    var db *Database

    func init() {
        // Выполнится один раз при импорте пакета
        log.Println("Initializing database...")
        db = &Database{}
    }

    type Database struct {
        // ...
    }

Функция `init` - особая в Go. Она **выполняется при инициализации**
программы, если пакет вошёл в сборку. Однако эти функции могут быть
**очень опасными**, считается **плохим тоном** их использование

4.  **Именование пакетов** При проектировании пакетов следует избегать
    "статтеринга" (stuttering) - повторения имени пакета в именах это
    экспортируемых идентификаторов.

Плохо делать так:

    package user

    func UserCreate() { /* ... */ }
    func UserDelete() { /* ... */ }

При использовании этих идентификаторов в других пакетах предстоит писать
так: `user.UserCreate()` - что является избыточным.

Лучше делать иначе:

    package user

    func Create() { /* ... */ }
    func Delete() { /* ... */ }

Тогда в других пакетах предстоит писать так: `user.Create()` - что
является понятным и не избыточным

5.  **Модули** Каждый Go-проект начинается с простой команды:

```{=html}
<!-- -->
```
    # Создание нового модуля
    go mod init github.com/username/project-name

После выполнения этой команды Go создает два важных файла: `go.mod` и
`go.sum`

-   **go.mod** - файл описания модуля и зависимостей;
-   **go.sum** - файл с криптографическими хешами заисимостей.

Остановимся подробнее на примере файла `go.mod`:

    module github.com/username/project-name

    go 1.25

    require (
        github.com/gin-gonic/gin v1.9.1
        github.com/golang-migrate/migrate/v4 v4.16.2
        github.com/lib/pq v1.10.9
        github.com/spf13/viper v1.16.0
        gorm.io/driver/postgres v1.5.2
        gorm.io/gorm v1.25.4
    )

    require (
        github.com/bytedance/sonic v1.9.1 // indirect
        github.com/chenzhuoyu/base64x v0.0.0-20221115062448-fe3a3abad311 // indirect
        // ... другие косвенные зависимости
    )

Файл состоит из списка используемых в проекте/модуле зависимостей,
делящихся на несколько секций:

а) `module` Определяет **имя модуля** - уникальный идентификатор проекта
в экосистеме Go:

    module github.com/username/project-name

Go автоматически умеет загружать зависимости напрямую из
git-репозиториев по указанному пути:

    module github.com/username/project-name  // Go будет искать репозиторий на github.com

    module gitlab.com/company/team/project   // Go будет искать на gitlab.com

    module golang.org/x/text                 // Go будет искать на golang.org

**Важные моменты:**

-   При использовании доменного имени Go ожидает найти действующий
    git-репозиторий;

-   Для приватных проектов можно использовать любое имя, но
    рекомендуется указывать домен для будущей совместимости;

-   Изменение имени модуля потребует обновления всех импортов в проекте.

б) `go`

Указывает **минимальную версию Go**, требуемую для сборки проекта:
`go 1.21`

с) `require`

Перечисляет **прямые и косвенные зависимости** проекта:

    require (
        github.com/gin-gonic/gin v1.9.1           // прямая зависимость
        github.com/golang-migrate/migrate/v4 v4.16.2 // прямая зависимость
        github.com/bytedance/sonic v1.9.1 // indirect  // косвенная зависимость
        github.com/chenzhuoyu/base64x v0.0.0-20221115062448-fe3a3abad311 // indirect
    )

**Прямые зависимости** - пакеты, которы импортируются напрямую в коде
проекта:

    import "github.com/gin-gonic/gin"  // прямая зависимость

**Косвенные зависимости** (`// inderect`) - пакеты, которые требуются
прямым зависимостям

d)  `replace` Позволяет подменить любую зависимость на другую версию или
    даже на локальный файл

```{=html}
<!-- -->
```
    replace github.com/old/package => github.com/new/package v1.2.3
    replace github.com/local/package => ../local/package

e)  `exclude` Работает как страж на границе - она говорит Go: "Эту
    версию загружать не нужно, пропускай!"

```{=html}
<!-- -->
```
    exclude github.com/problematic/package v1.5.0

**go.sum** Содержит **криптографические хеши** всех зависимостей проекта
и обеспечивает безопасность и воспроизводимость сборок

    github.com/gin-gonic/gin v1.9.1 h1:4idEAncQnU5cB7BeOkPtxjfCSye0AAm1R0RVIqJ+Jmg=

    github.com/gin-gonic/gin v1.9.1/go.mod h1:hPrL7Yrp6KXt5YId3A/Tnip5kqbEAP+KLuI3SUcPTeU=

    github.com/bytedance/sonic v1.9.1 h1:6iJ6NqdoxCDr6mbY8h18oSO+cShGSMRGCEo7F2+0Y8=

    github.com/bytedance/sonic v1.9.1/go.mod h1:i736AoUSYt75HyZLuJZ0SSRlHkmaJ2Kl9N6Fz5rD3k=

Каждая строка содержит: - **Путь к модулю** - имя пакета; - **Версия** -
конкретная версия или коммит; - **Хеш** - криптографическая подпись
пакета

6.  **Работа с зависимостями** - **go get** Общий пайплайн может быть
    таким:

```{=html}
<!-- -->
```
    # Добавление последней версии пакета
    go get github.com/gin-gonic/gin

    # Добавление конкретной версии
    go get github.com/gin-gonic/gin@v1.9.1

    # Добавление последней версии пакета
    go get github.com/stretchr/testify@latest

    # Обновление всех зависимостей
    go get -u ./...

    # Удаление неиспользуемых зависимостей
    go mod tidy

7.  **Собрать и установить исполняемые файлы** - **go install** Собирает
    в директорию `$GOBIN` (по умолчанию - `$GOPATH/bin`).

    Чтобы потом запускать установленные утилиты из терминала, добавь
    `$GOBIN` (или `$(go env GOPATH)/bin`) в `PATH`

Самый частый сценарий - **поставить внешние** инструменты разработки
(линтеры, генераторы, форматтеры) так, чтобы они **не трогали** `go.mod`
**проекта**.

Для этого указываем версию через `@...`:

    # форматтер/инструменты x/tools
    go install golang.org/x/tools/cmd/goimports@latest

    # линтер (пример — версию можно закрепить)
    go install github.com/golangci/golangci-lint/cmd/golangci-lint@v1.55.2

8.  **Важная информация о базовых проектах** - **internal** и **pkg** Go
    предоставляет особый механизм для ограничения доступа к пакетам
    модуля

    Любой пакет внутри директории `internal` доступен только для пакетов
    этого модуля:

**internal**:

    my-module/
    ├── internal/
    │   └── database/  // доступен только внутри my-module
    ├── api/
    │   └── handler.go // может импортировать internal/database
    └── client/
        └── main.go    // может импортировать internal/database

Но что, если все-таки необходимо поделиться с миром каким-то пакетом из
текущего сервиса/модуля? В этом случае можно использовать `pkg` **pkg**

    my-module/
    ├── internal/
    │   └── database/  // доступен только внутри my-module
    ├── pkg/
    │   └── csv_converter/  // доступен и внутри my-module, и вовне его при импорте my-module в другие модули
    ├── api/
    │   └── handler.go // может импортировать internal/database
    └── client/
        └── main.go    // может импортировать internal/database

9.  **Типичные структуры**

-   **server project** - часто выбирают для реализации серверов

```{=html}
<!-- -->
```
    project-root-directory/
      go.mod
      internal/
        auth/
          ...
        metrics/
          ...
        model/
          ...
      cmd/
        api-server/
          main.go
        metrics-analyzer/
          main.go
        ...
      ... остальные директории проекта с не-Go кодом

-   В данной структуре явно понятно, что **нет экспортируемых пакетов
    Go** - четко видно, что Go код написан в
    директориях `internal/` и `cmd/`. Серверные проекты часто замкнутые
    и поэтому им не требуется экспортировать пакеты;

-   **Отдельно выделена** директория `cmd/` с точками входа;

-   Все остальные директории **могут использоваться как угодно** -
    различать Go код они никак не помешают. Например, в корень проекта
    можно добавить `docker/`, `chart/`, `.gitlab/` и прочее.

# Tooling

Код должен быть удобен для чтения. Но и не только для тебя но и для
твоих коллег

#### Зачем нужен тулинг

-   Для того чтобы выдерживать единое оформление кода в разных файлах в
    условиях одновременной разработки сервиса несколькими
    разработчиками.
-   Это также возможность избегать странных конструкций, которые сам
    компилятор пропускает (например, функцию с множеством циклов,
    которые повышают когнитивную нагрузку на разработчика при чтении
    кода).
-   Ещё тулинг помогает чистить импорты, дублирование кода.
-   Определяется проблема с конкурентностью и зависимостями.

**Идея проста:** Пишем код =\> форматируем его =\> проходим статические
проверки =\> проходим тесты =\> коммитим код в ревью

В Golang имеется два типа инструментов, которые можно использовать:

1.  Встроенные в экосистему:

-   `gofmt`;
-   `go test`;
-   `go vet`;
-   `go doc`.

1.  Внешние инструменты:

-   `gopls`;
-   `goimports`;
-   `golangci-lint;`
-   `govulncheck`.

Здесь важно понять, что это те самые инструменты, с которыми
разработчики вплотную работают повседневно.

Нам необходимо установить три инструмента, пропишем команды:

    go install golang.org/x/tools/gopls@latest
    go install golang.org/x/tools/cmd/goimports@latest
    go install golang.org/x/vuln/cmd/govulncheck@latest

#### Встроенный тулинг Golang

**Форматирование кода**

В Go о форматировании не спорят. Требуется всего-навсего использовать
стандартный форматер `gofmt`

Можно отформатировать все файлы текущей директории и все её
поддиректории:

    go fmt ./...

Но также можно отформатировать конкретный файл:

    gofmt -w file.go

Весь проект можно отформатировать командой:

    gofmt -w .

#### Более умное форматирование

`goimports` - мало того, что автоматически обновляет строки импорта,
удаляя и добавляя недостающие зависимости, она еще и форматирует код
ровно так же, как и `gofmt`!

Запускается:

    goimports -w main.go # Форматирование конкретного файла

    goimports -w . # Форматирование всего проекта

#### Как организована помощь в редакторе

Форматеры помогают после написания кода привести его в порядок. Но
утилита `gopls` делает иное: она помогает непосредственно во время
работает.

Подобный сервер позволяет интегрировать в IDE определённые возможности
для работы с конкретным языком:

-   \`подсветку ошибок в редакторе;
-   `переходы к определению функции/переменной;`
-   `поиск использования функций/переменных;`
-   `автодополнение;`
-   `встроенные подсказки.`

Если честно говорить, то редактор без `gopls` - это не самый лучший
редактор для Go. Утилита позволяет увидеть множество проблем в коде ещё
до запуска тестов и линтеров.

1.  **Очищение кода от подозрительных вещей** - **go vet** Позволяет
    очищать странный и неидиоматичный код

-   проверка бесполезных объявлений переменных;
-   проверка типичных ошибок при работе с пакетом `sync/atomic`;
-   проверка неиспользуемого кода и многое другое.

Важно, что `go vet` не гарантирует, что в коде не останется проблем. Он
только ищет странные вещи

    go vet ./...

2.  **Линтеры** - **golangci** Класс инструментов, которые автоматически
    проверяют исходный код на наличие ошибок и стилевых нарушений

-   проверка на ограничение длины строки;
-   проверка на цикломатическую сложность;
-   проверка на длину функции и так далее.

Это очень удобный и гибкий инструмент, который не только запускает
несколько линтеров, но и быстро работает, выводит всю информацию после
аналитики со ссылками на строки

Примером настройки `golangci` через yaml может служить файл:

    run:
      timeout: 5m
      modules-download-mode: readonly
      
    linters:
      disable-all: true # Отключить всё по умолчанию
      enable:          # Что включено принудительно
        - errcheck     # Проверка необработанных ошибок
        - goimports    # Проверка импортов
        - golint       # Рекомендации по стилю (устаревает, но полезен)
        - govet        # Тот самый go vet!
        - staticcheck  # Статический анализ
        - unused       # Неиспользуемый код
        - gosimple     # Упрощение кода
        - bodyclose    # Закрытие http тел
        - dupl         # Поиск дублирования кода
        - reassign     # Поиск переопределения переменных
        - unconvert    # Лишние приведения типов
          
    issues:
      exclude-use-default: false # Не использовать стандартные исключения
      max-issues-per-linter: 0   # Показать все ошибки
      max-same-issues: 0         # Показать все похожие ошибки
      exclude-rules:
        - path: _test\.go
          linters:
            - goconst    # Игнорировать дублирование строк в тестах

Но здесь стоит быть довольно осмотрительным. Порой к линтерам начинают
относиться слишком религиозно, стараясь получить идеальный код

Что точно плохой подход при работе с линтерами:

-   Включать все линтеры подряд.
-   Получать сотни предупреждений и гасить их (делать невидимыми для
    линтера) через директиву `//nolint`.
-   Начинать чинить линтером код, а не улучшать его.

Вместо этого всё-таки стоит действовать немного иначе

> \[!NOTE\] Линтеры - это ещё один гарант качества кода в 95% компаний,
> так что стоит научиться жить и работать с ними.

3.  **Проверка зависимостей** - **govulncheck** Проверяет используемые в
    проекте зависимости на предмет известных уязвимостей:

    govulncheck ./...

### Чеклист перед PR

Перед отправкой на ревью стоит выполнить небольшой список программ:

    gofmt -w .
    go vet ./...
    golangci-lint run
    go test ./...
    go test -race ./...
    govulncheck ./...

Это позволит убедиться, что с точки зрения написанного кода к тебе не
подкопаться.
